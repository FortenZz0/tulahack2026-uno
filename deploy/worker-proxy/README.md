# Прокси API на VPS

Прокси принимает HTTPS-запросы по адресу `https://tg.filinda.ru/exoplanet-api/`
и пересылает их существующему Cloudflare Worker. KV, Durable Objects,
обновление NASA и генерация описаний остаются на Worker.

## Подключение к существующему Nginx

Конфигурация рассчитана на сервер, где уже работает HTTPS для `tg.filinda.ru`.
Она добавляет только путь `/exoplanet-api/`, сохраняя обработку других адресов.
Перед применением нужно проверить текущий веб-сервер, его конфигурацию
и доступность Worker с VPS.

1. Сохранить `exoplanet-api.conf` на VPS, например как
   `/etc/nginx/snippets/exoplanet-api.conf`.
2. Внутри существующего HTTPS-блока `server` домена `tg.filinda.ru` добавить:

   ```nginx
   include /etc/nginx/snippets/exoplanet-api.conf;
   ```

3. Проверить конфигурацию и применить её только после успешной проверки:

   ```bash
   sudo nginx -t
   sudo systemctl reload nginx
   ```

На Debian/Ubuntu используется набор доверенных сертификатов
`/etc/ssl/certs/ca-certificates.crt`. На другой ОС путь в
`proxy_ssl_trusted_certificate` нужно уточнить. Если перед Nginx стоит ещё
один прокси, его таймаут также должен позволять дождаться описания.

Конфигурация разрешает DNS-имя Worker только в IPv4 и обновляет адреса через
DNS без перезагрузки Nginx. Проверка сертификата upstream включена, максимальная
глубина его цепочки явно установлена в 5.

DNS домена должен вести к доступному VPS напрямую; проксирование самого
`tg.filinda.ru` через Cloudflare сохранит исходную проблему доступа.

## Маршруты и проверка

| Адрес на VPS | Адрес на Worker |
| --- | --- |
| `/exoplanet-api/preview` | `/preview` |
| `/exoplanet-api/full` | `/full` |
| `/exoplanet-api/planets` | `/planets` |
| `/exoplanet-api/stars` | `/stars` |
| `/exoplanet-api/desc?id=…` | `/desc?id=…` |

Другие пути внутри `/exoplanet-api/` возвращают 404. Адрес upstream фиксирован;
пользователь не может использовать конфигурацию для запросов на произвольные сайты.
Ответы и CORS-заголовки передаются от Worker без дополнительного кэширования.

Проверки без генерации платного описания:

```bash
curl --fail --max-time 30 https://tg.filinda.ru/exoplanet-api/preview
curl --include --max-time 30 https://tg.filinda.ru/exoplanet-api/desc
```

Первый запрос должен вернуть JSON каталога с HTTP 200, второй — HTTP 400
из-за отсутствия `id`. После этого доступность проверяется из российской сети.

## Переключение фронтенда

Каталог использует адрес в `app/lib/api.js`; клиент описаний создаётся
в `app/main.js`. Оба клиента настроены на базовый адрес
`https://tg.filinda.ru/exoplanet-api/`.

Клиент описаний должен сохранять префикс `/exoplanet-api/` при построении URL
и кодировать `id` через `URLSearchParams`. Замена только домена без учёта
префикса отправит запрос описания на неправильный путь `/desc`.

Перед публикацией новой сборки нужно проверить оба каталога через прокси
и запрос `/desc` без `id` (ожидается HTTP 400). Установка прокси на VPS сама
по себе не публикует изменения фронтенда: сайт нужно собрать и развернуть отдельно.
